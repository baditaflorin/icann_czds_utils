# Domain-slice pipeline runbook

How a CZDS zone file becomes fixed-size domain slices, how each slice is run
as a container against the domainscope categorizer, and the operating rules
learned doing it at scale.

## What is and is not in git

| Thing | In git? |
|---|---|
| These tools (`make_all_chunks.py`, `deploy_tld.py`, ...) | yes |
| Zone files (`zone_files/*.txt.gz`; `com` is ~4.6 GB) | **no**: gitignored, and CZDS terms restrict redistribution. Re-download with your own CZDS account or copy them over. |
| `data/czds.db` (SQLite, large) | **no** |
| Generated slice lists (`domains.txt`, ~8.7 MB per 500k) | **no**: regenerate from the zone file |
| Per-slice `main.go` / `Dockerfile` / `docker-compose.yml` | generated by `deploy_tld.py` from templates in that file |
| Per-slice progress | lives only in each container's logs and its compose `START_ID` |

## 1. Generate slices (streaming, O(1) memory)

```bash
python make_all_chunks.py --zone-file zone_files/com.txt.gz --output-dir com_splits --dry-run  # counts only
python make_all_chunks.py --zone-file zone_files/com.txt.gz --output-dir com_splits            # com-<letter>-<NN>.txt
```

- One series per letter `a`-`z`, plus `0` for names starting with a digit.
  500,000 domains per file; numbering starts at 01.
- Only second-level names are kept (`example.com`, not `ns1.example.com`).
- Relies on the zone being sorted by name (CZDS zones are) to drop duplicates
  with O(1) memory; it warns if it sees out-of-order names (then run the zone
  through `sort -u` first).
- Rough size for the whole `.com` zone: about 17.7 bytes/domain, so ~2.8 GB of
  text across ~320 files if `.com` has ~160M names (an assumption; `--dry-run`
  gives the real count). `make_next_chunks.py` is the older continue-after-
  boundary tool; it keeps a set of every domain in memory, so avoid it for all
  letters at once.

## 2. Deploy a slice

```bash
export DEPLOY_JUMP_HOST=user@bastion DEPLOY_HOST=<target-ip> DEPLOY_USER=<user>
python deploy_tld.py --from-file com_splits/com-a-01.txt --name com-a-01 --skip-dns-filter
```

Defaults are `CONCURRENCY=1`, `DELAY_MS=1000`. Each worker paces itself at one
request per `DELAY_MS`, so a container sends `CONCURRENCY * 1000 / DELAY_MS`
requests/s. Earlier versions shared one ticker across all workers, which made
`CONCURRENCY` a no-op; that is fixed in the template, so old defaults of 13
workers / 2000 ms would now mean ~6.5 req/s per container. Do not restore them.

## 3. Operating rules (each one came from a real incident)

1. **Resume point = last processed ID + 1, read from the container's own log
   before recreating it:** `docker logs <c> | grep 'Processing ID' | tail -1`.
   Recreating a container discards its log; use a central log store if you
   have one to confirm a resume point afterwards.
2. **Edit `docker-compose.yml`, then `docker compose up -d --force-recreate`.**
   Plain `up -d` after `stop` restarts the old container object with its old
   environment.
3. **Check for `docker-compose.override.yml` first.** Compose merges it over the
   base file and it wins silently. Pinned `START_ID`s in override files made
   every edit to the base file a no-op once.
4. **Verify after every start.** The first log line prints the effective
   `START_ID=`; it must match what you intended.
5. **Containers have no restart policy by default.** After a host reboot they
   stay down; Docker then shows a blank STATUS and a zero `FinishedAt` for
   containers that were killed uncleanly.
6. **Do not blame the pipeline for host load by default.** Check the top CPU
   consumers before cutting concurrency; an unrelated process (headless
   browser bursts, caches, proxies) is often the cause.

## 4. Capacity

- A container is a small Go process that streams its file line by line (I
  estimate 10-30 MB; not measured). Disk and RAM are not the constraint.
- The constraint is the shared search path behind the categorizer. In
  practice ten containers at `CONCURRENCY=1` produced ~45 categorizations/min
  and 2-3 workers each roughly 100-150/min. At ~150/min, 160M domains is on
  the order of two years of wall time, and adding containers does not help
  once the search path throttles.
- Cheaper levers: the DNS filter in `deploy_tld.py` (on by default) drops
  names that do not resolve (about 28% in one sample); many resolving names are
  parked and return no search results (HTTP 404, expected, ~50-60% of
  attempts); the API answers already-known domains from cache.
- Agree a total concurrency budget before starting many containers at once.

## 5. New-server checklist

- Docker + Compose; outbound HTTPS to `domainscope.scrapetheworld.org`
  (`DOMAINSCOPE_API_IP` only if it must be pinned to an internal gateway).
- The zone file (copy `com.txt.gz`, or re-download using `CZDS_USERNAME` /
  `CZDS_PASSWORD` in an untracked `.env`).
- Run `make_all_chunks.py` there (streaming, no large RAM needed), then deploy
  slices in waves sized to the concurrency budget, not all ~320 at once.
